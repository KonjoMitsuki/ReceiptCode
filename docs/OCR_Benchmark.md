# OCR Benchmark

## 起動・操作

```bash
npm ci
npm run dev
# http://localhost:5173/receipt2jan/
```

この比較用ブランチではトップページがベンチマークです。`BASE_PATH=/ npm run dev` なら `/`、静的ビルドも配信ルート（サブパスの場合はその直下）で開けます。mainブランチの通常の撮影→JAN解析→バーコード生成は変更しません。このブランチで元のフローを確認する場合のみ `?receipt-flow` を付けられます。

1. JPEG / PNG / WebPを1〜複数枚登録（1枚10MB以内）。画像はIndexedDBに保存します。
2. 正解データは**入力しなくてもOK**。精度も測りたい場合だけ、画像ごとの「正解データを入力して精度も測る（任意）」を開いて入力します。全文を登録すればCER・差分、商品名/JANを登録すればそれぞれの一致率を計算します。商品名・JANは1行1件で重複明細も同じ件数を登録。JANは半角数字8桁/13桁。
3. 比較対象画像とエンジンを選択。初期値はTesseract・Paddle、画像処理は **none（分割なし）**。
4. 一括比較で正解も保存。エンジン・画像ごとに新規初期化して**逐次実行**し、CPU/メモリの競合を避けます。結果は横並び（小画面は縦並び）です。
5. 正解の有無にかかわらず、**mainと同じレシート解析・JAN確認画面（商品名・JAN候補・確認チェック）**をエンジンごとに並べて見比べます。カードの編集・確認・手動追加と「次へ」からのバーコード表示も利用できます。編集は比較画面だけの一時状態で、履歴にはOCR原文を保存します。初期化・認識・総所要、モデル・必須前処理、入力サイズ/SHA-256を確認でき、OCR原文・差分は詳細を開いた場合だけ表示します。正解の登録があればCER/JAN/商品名も表示。比較履歴を再表示・削除できます。

画像・正解・結果は当該ブラウザ/オリジンの `receiptcode-ocr-benchmark` IndexedDB（スキーマ1）だけに保存します。履歴には実行時の正解・モデル・前処理をコピーするため、後の正解編集では過去の数値は変わりません。「画像と関連履歴を削除」はその画像の正解と、その画像を含む比較履歴全体を削除します。通常フローには履歴保存を追加していません。共有端末では利用後に削除してください。サイトデータ削除・保存容量不足・プライベートブラウズ等で消失/保存失敗する場合があります。

## エンジン・同一条件

| エンジン | モデル/設定 | 内部の必須前処理 |
|---|---|---|
| Tesseract.js 7.0.0 | `jpn`のみ、LSTM、PSM.AUTO、DPI=300、空白保持 | Leptonicaでデコード・二値化・レイアウト解析 |
| 公式 `@paddleocr/paddleocr-js` 0.4.2 | PP-OCRv5_mobile_det + PP-OCRv5_mobile_rec（日本語対応の多言語モデル）、ONNX Runtime 1.24.3 WASM、1スレッド・認識バッチ1 | 検出リサイズ（長辺最大960px）、正規化、文字領域切り出し、認識リサイズ |
| Google Cloud Vision | オンライン `DOCUMENT_TEXT_DETECTION` / `languageHints: ja` | 同じ原画像をbase64化。内部前処理・モデル版は非公開 |

通常フローのTesseract `jpn + eng`、最大2400px/JPEG化は維持します。比較ではそのアプリ前処理を通さず、**同じ原Blob**を各アダプターへ渡します。エンジン内の必須処理やGoogleのネットワーク時間を同一化できるとは主張しません。

共通契約は `src/lib/ocr.ts` の `OcrEngine`（`recognize` / `dispose`、キャンセル・進捗、任意の時間内訳）。比較ランナーは `ImageStrategy` をエンジンループ外で一度適用し、同じ処理済み入力を渡せる構造です。現在は `none` のみで、複数分割は分割ごとの正解対応付けを実装するまで拒否します。

初期化/認識/総所要は `performance.now()` による実測です。

- 初期化: ファクトリー生成、遅延ロード、Worker起動、モデル/資材取得、パラメーター設定まで。
- 認識: 内部前処理・デコードを含む認識呼び出し。Googleはプロキシ/Googleとの通信も含みます。
- 総所要: ファクトリー生成からWorker終了まで。ハッシュ・共通指標計算・IndexedDB保存は除外します。
- 集計時間は成功結果の平均。失敗/中止は精度・平均時間に混ぜず件数を別表示し、個別の総所要時間は記録します。未実行エンジンは結果を作りません。
- 各実行は新しいWorkerですが、HTTP/モデルキャッシュは削除しません。初回/再実行・回線・端末・ブラウザ負荷に左右されます。絶対的な性能順位ではなく、同一端末・同一条件で繰り返し比較してください。

## 指標

- **CER**: Unicodeコードポイント単位のLevenshtein編集距離 / 正解文字数。CRLF/CRのみLFへ統一し、空白・全半角・大小文字は維持します。挿入が多ければ100%超になります。
- 正解テキストなしの場合はCER・差分を計算しません。商品名/JANだけを登録した場合も、それぞれの一致率は計算します。正解データが全くない場合でも、JAN確認画面・処理時間・履歴を表示します。OCR原文は各結果の詳細から確認できます。
- **JAN完全一致率**: 全エンジンに共通の既存レシートパーサーで抽出した8/13桁候補と、手動正解JANの完全一致件数 / 正解件数。チェックデジット判定とは別です。
- **商品名正解率**: 同じ共通パーサーがJANに関連付けた商品名と、手動正解名の完全一致件数 / 正解件数。OCRだけでなく既存のJAN/商品名対応付けも含むend-to-end指標です。JANを含まないレシートの独立した商品行検出率ではありません。
- 重複は1件ずつ消費します。JAN/商品名の分母0は「—」（100%とはしません）。余分な候補の適合率は今回の指標に含みません。
- 集計精度は成功結果の誤り数/件数を合算した**マイクロ平均**。失敗・中止件数も合わせて比較し、異なる成功サンプルだけの順位を過大解釈しないでください。
- 差分: 下線=挿入、二重下線=置換、取り消し線=欠落した正解文字。ホバー説明/読み上げテキストも用意。巨大な差分行列（200万セル超）はハイライトだけ省略します。

## プライバシーとGoogle比較

**本番OCRはローカルファーストを維持します。** Tesseract・Paddleは端末内Workerで実行し、画像/OCR結果を外部送信しません。初回には以下の**資材だけ**を取得します。

- Tesseract: jsDelivrのWorker/core/`jpn`言語データ（通常フローは`eng`も）。
- Paddle: 同梱の公式Worker/OpenCV、jsDelivrの `onnxruntime-web@1.24.3/dist/`、公式 `paddle-model-ecology.bj.bcebos.com/paddlex/official_inference_model/paddle3.0.0/` のPP-OCRv5 mobile ONNXモデルtar。

PaddleのモデルURLには、配布CDNのCORS応答をオリジン別にキャッシュするため `receiptcode-origin`（アプリの公開Originのみ）を付加します。画像・正解・認識結果は付加しません。

Paddleは大きなモデル/WASMを扱い、モダンブラウザのWorker/ImageBitmap/OffscreenCanvas等が必要です。資材は遅延ロードし、通常フローでは取得しません。端末によって起動失敗/メモリ不足があり得ます。実機Safari/Androidでの性能検証は未完了です。

省メモリ化のため、SDK本体を画面側に読み込まず、公式WorkerだけでOpenCV/ONNXを実行します。`paddleEngine.ts` の通信形式はSDK 0.4.2に固定しており、更新時は実Workerで初期化→認識→終了の確認が必要です。検出画像の上限を4000pxから960px、認識バッチを1に制限したため、旧履歴とは前処理条件が異なります（各結果に記録）。原Blobは他エンジンと同一です。Workerのエラー・通信失敗・180秒の無応答は失敗結果として扱い、完了・失敗・中止のいずれもWorkerを終了します。

Googleは**開発者向け比較のみ・デフォルト無効**。有効化したい開発者だけ、Git管理外の `.env.local` に設定します（`.env.example` 参照）。

```dotenv
OCR_BENCHMARK_GOOGLE_ENABLED=true
GOOGLE_CLOUD_VISION_API_KEY=your-server-only-api-key
```

Cloud Vision APIと課金を有効にしたプロジェクトで、Vision APIに利用制限したキーを使い、予算/クォータも設定してください。**`VITE_` 接頭辞を付けず、キーをコミットしないでください。** 設定後は開発サーバーを再起動します。

- ローカルHTTP開発サーバーの `/api/dev/ocr-benchmark/vision` のみが仲介します。loopback接続/Host・Originを検証し、画像形式、10MB上限、同時実行、60秒タイムアウト、送信同意ヘッダーを検証します。HTTPS終端プロキシ/外部公開は対象外です。
- UIでGoogleを選び、送信対象枚数と処理条件を確認し、その実行の同意にチェックするまで送信できません。対象/条件を変更した場合や実行終了後は同意をリセットします。
- アプリ側サーバーは画像・結果をメモリ内だけで中継し、ファイル/DB/ログへ永続保存しません。キーやGoogleのエラー詳細をクライアントへ返しません。リバースプロキシ等でリクエスト本文ログを追加しないでください。
- `npm run build` / `preview` / GitHub Pages等の静的配信にはAPIを含めません。Googleは無効でもローカルエンジンは利用できます。
- Googleの[データ利用条件](https://cloud.google.com/vision/docs/data-usage)（2026-10-26確認）ではオンライン画像はメモリ内処理、コンテンツはモデル学習に使用されません。ただしリクエスト時刻/サイズ等のメタデータは一時記録されます。「Google側にも一切保存されない」とは保証しません。[Cloudデータ処理追加条項](https://cloud.google.com/terms/data-processing-addendum)と所属組織の規程を利用前に確認してください。オフライン非同期APIは使用しません。

顧客情報を含む実レシートはGitに追加せず、使用権限・店舗規程を確認してください。Googleへ送る場合はさらに外部送信の許可が必要です。

## 検証

`npm test` は厳密CER/差分/重複照合/集計、同一Blob/逐次実行/エラー継続/中止、IndexedDB、Googleの無効/同意/Origin・Host/上限/サーバーキー/エラー秘匿を検証します。`npm run test:e2e` はローカルOCRを固定エンジンに置き換え、比較画面と既存のJAN/バーコードフローを検証します。Google E2Eは通信モックで、実APIを呼びません。

実装時にはChromiumの静的ビルドで架空レシート `tests/fixtures/receipt-sample.png` を実際のTesseract/Paddleに渡し、両方の認識完了・入力SHA-256一致・資材GET以外の外部通信なし・履歴再読込・日本語UIの320px表示を確認しました。これは精度を保証する実レシート評価ではありません。Google実APIは認証情報未設定のため未実行です。

2026-10-27の省メモリ修正では、Linux上のChromium・WebKitで同じ架空レシートと3024×4032pxに拡大した画像を実Paddleで認識し、画面側にOpenCV/ONNXがロードされないことを確認しました。静的ビルドでも両エンジンのJAN確認画面表示・ページ例外なしを確認しています。WebKitでの検証はiPhone実機のメモリ制限を再現するものではなく、報告された実機での再確認は必要です。
